##### OPSX Looping Skill 소개
- 전체 흐름: `explore → refine → propose → implement → in review → review-pr → monitor-pr → deploy-verification → done`
- cron으로 implement, review-pr, monitor-pr, deploy-verification 돌림 (loop skill 활용)
- `opsx:cron all`로 각 step을 looping
- Jira board 기반 매핑:
	- rough ideas → explore 후
	- spec drafting → propose 단계
	- backlog → spec 완성 시
	- ready for automation → AI agent가 자유롭게 pickup, implement, PR
	- awaiting human ops → 사람 개입 필요
	- deploy verification → 배포 체크
- spec 작성 → OpenSpec 기반. taskmaster-ai는 implement agent가 활용
- `opsx:explore`로 스펙 brainstorming → "Rough Ideas" lane에 티켓 생성

##### Paradigm

**SDD (Spec-Driven Development)**
- OpenSpec 기반 타이트한 조건의 spec doc. spec delta 작성
- 작성된 spec은 task로 분해. local도 저장
- capability에 따른 스펙 구분. archiving spec docs

**Harness Engineering**
- "모델이 다 해결해줄거다" → 아직은 아닌걸로
- 핵심은 Progressive Disclosure
- golden principles를 레포에 코드화하는 정리적 정리 Loop
- 내 아이디어 → 문맥을 잘 이해하는 skill을 여러개 만들어, 각 skill에 대한 최적화 진행
- Spec 문서에 대한 디테일한 작성
- harness는 진화한다. 모델 능력이 올라가면, 더 복잡도가 높은 문제를 풀어야 한다
- observability 확보 → playwright mcp, agent-browser

**AI Workflow Design**
- Task routing — 티켓 사이즈에 따라 어떤 flow를 탈지 (full spec definition vs debugging)
- Task ordering — task analysis(taskmaster-ai), ticket analysis
- Task throttling — monitoring + cron. 빠르게 시도했을 때 시스템이 충분히 warmup 되지 않을 수 있음

**Parallelizing Task Management**
- 도구: cline/kanban, openai/symphony, makeplane/plane
- 핵심 질문: 어떻게 parallel하게, conflict 없이, 효율적으로 schedule 할 것인가

**Global Looping vs Local Looping**
- local looping의 한계 — 틀을 벗어나는 변경을 만들기 힘듦
- session-wrap = 그 세션 기준 context 업데이트 = **local minimum** 찾기
- 전체 context를 숲을 보는 눈으로 리팩터링 = **global minimum** 찾기
- 두 가지 루프를 따로 운영

**AI Workflow Pattern**
- planner → generator → evaluator 패턴
- Plan → Implement → Evaluate → **Improve**
- 더 구체적으론: explore → spec → implement → test → validate → reflect → improve
- 어떤 loop를 돌든 이 4가지 flow를 따름
- ex) merge agent: Plan(dependency 정리 + CI) → Implement(merge) → Evaluate(deploy 체크) → Improve(누락 체크)

**Minimizing the Input Surface**
- **"에이전트가 접근할 수 없는 것은 존재하지 않는 것과 같다."**
- 시스템의 input surface는 1개가 가장 좋음
- agent가 추적할 수 없는 input이 많을수록 중요한 context 누락
- 여러 input surface → 전체 통합 검색 필요 → 복잡, 싱크 문제
- output surface는 여러군데여도 OK

**Managing Comprehension Debt**
- ARCHITECTURE.md — architecture.md 템플릿 활용
- RELIABILITY.md, SECURITY.md, DESIGN.md 등 지식 구조 설정
- Manual QA 유지
- Notion docs / Mermaid UML / Slack notification / summaries
